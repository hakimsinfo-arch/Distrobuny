How it was made

Distro Buny is an original multiboot system: its menu, its way of starting distributions and its disk-image tools were written for this product. It uses standard, signed building blocks (shim, GRUB, a Linux kernel) but no existing multiboot product. This document gives an overview; the source archive's documentation/ folder has the full technical details.

1. The idea

A multiboot stick should be as simple as a folder of ISO files: copy images on from any computer, start from the stick, pick one. The hard part is that every distribution expects to start from its own DVD and looks for that DVD in its own way. Distro Buny solves this by starting a small Linux system of its own first, and from there handing the computer over to the chosen distribution, together with a virtual DVD made from its ISO file.

2. The stick

  BUNY-EFI     FAT32, 512 MiB   boot chain, Distro Buny runtime, settings
  DISTROBUNY   exFAT, the rest  your ISO files (readable and writable everywhere)

exFAT was chosen because Windows, macOS and Linux can all write it and it has no 4 GB file-size limit. The data partition sits at the end of the stick, so the menu can grow it to the stick's full size after the image was written; that step only rewrites bookkeeping and is designed to survive a power cut.

3. From power-on to a running distribution

  1. Firmware → shim → GRUB. Microsoft-signed shim and Canonical-signed GRUB, so the stick starts whether Secure Boot is on or off.
  2. The Distro Buny runtime. Canonical's signed Linux kernel with Distro Buny's own small system: buny-init (finds the stick, loads drivers, does everything that needs privileges) and buny-ui (the graphical menu, running without privileges because it reads untrusted ISO files).
  3. Reading the ISO files. The menu reads each image's own boot menu (GRUB, systemd-boot, isolinux), recognises the distribution family and its version, and checks the kernel's signature.
  4. The virtual DVD. The ISO file's exact position on the stick is mapped, and a small Distro Buny program placed in front of the distribution's own startup code presents the file as a read-only disk with the ISO's name and ID.
  5. Hand-over. The runtime loads the distribution's kernel with kexec and jumps into it. From then on the distribution runs exactly as from its own DVD.

4. Supporting many distributions

Distro Buny recognises a system by how it starts, not by its name, through "adapters", one per family of startup code:

Because the recognition works on the boot method, new releases and derivatives of these families work without changes. A 64-bit Linux image of a family Distro Buny does not know is still offered ("best effort") and started after a confirmation.

5. Safety and stability

  • The menu runs without privileges; the privileged part accepts only a few checked requests.
  • ISO files and the data partition are only read while a system runs; the virtual DVD is read-only.
  • Distro Buny never writes to the computer's own disks, and it changes its own stick only when asked (and only the stick the computer was started from).
  • Images that erase a disk by themselves (self-installers, unattended installers) are detected and need an explicit confirmation, with Cancel as the default.
  • Distro Buny never bypasses Secure Boot. With Secure Boot on, only kernels signed by keys its Ubuntu-signed runtime trusts can be started (in practice the Ubuntu family), and the menu says so before you try; with Secure Boot off, every supported system starts.
  • Growing the data partition writes in a crash-safe order and finishes by itself after a power cut.
  • The ISO and boot-menu readers were run against thousands of deliberately corrupted images under memory-error detectors, without a single crash.

7. How it was tested

  • Every boot was tested in QEMU virtual machines with UEFI firmware (OVMF), with and without Secure Boot, the stick attached as a USB drive, through the complete chain from the firmware to the distribution.
  • 54 real distribution images, downloaded from the projects' official servers and checked against their published checksums or signatures: all 54 start (the Debian installer since the fix of 28 October 2026). With Secure Boot on, 15 start (all signed by Canonical) and the other 38 are correctly refused.
  • Automated tests: C unit tests (118 checks), image-writer, release and installer tests (51), menu tests driven by keyboard and mouse (25), and virtual-machine tests of the starter image (growing the stick, power cuts), the menu, Secure Boot and fragmented files.
  • Every disk image and every grown stick is checked with the reference tools fsck.exfat and fsck.fat; growing the stick was tested with a simulated power cut after every single write.
  • The release folder is checked by the build tool itself: every file and every checksum quoted in the documents must match.
  • Not yet done: tests on a wide range of physical PCs and USB sticks.
